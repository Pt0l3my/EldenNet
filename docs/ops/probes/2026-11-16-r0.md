# R0, 2026-11-16: the first real report of the derivation's offline round

The reviewed record of the file R0 returned (O89 (3)), in our own words. It holds the report's counts only: no byte,
pattern, offset or text of the game's executable, and nothing of the owner's. The entries behind it are WHY§180 to
§189.

## The run

- **Date**: 2026-11-16, on the owner's PC, with the game closed.
- **Build**: 2.7.2.0, region `ww`.
- **How**: DataPiler 0.2.41's job ran the engine's `probe-exe --derive` on the game's executable with the leads, then
  the lint on its report (O89 (1), DataPiler DP36). probe-exe exited 1 ("something not derived"), the lint passed
  (exit 0), and the report is 6,699 bytes of `derive.json`'s schema 1. The run worked end to end.
- **SHA-256**:
  - tool: `6657b8b48aa36f473e5e57eebece236bd45454bbe126b3bcd7d3d5f4366f3913`
  - leads: `20bf82f68e1287ef3483f1fc04e4532b6910aced0c5891660da71000704e8dfc`
  - report: `b774361be88035a4319ac248b9f07872a3c75185087aa63d61e946a673b77209`
- **Reviewed** with `python3 -I`, as data, against the engine's code that produced each number (`feat/engine` at
  d3f1935).

## What each finding meant

1. **The PE reader and the RTTI walk work.** 11 sections, 235,897 functions in the exception directory and 455,004
   base relocations were read, so R0b's loader rules held (WHY§171); the version resource gives 2.7.2.0 and `ww`.
   10,202 complete-object locators, one vtable each. The character class has one type descriptor and 6 classes
   counting itself; the player's class has 2, both among those 6. Which classes they are is R1's to confirm: the report
   names none. Both descriptors lie in the file-backed part of `.data`, as statically initialised RTTI should.
2. **The FD4 finder failed by a bug of the kit's, not by a fact of the game's.** 3 path strings, 9,837 references to
   them, 7,095 of them behind an accessor's head (2,742 with none, which R0 does not explain), 6 head shapes, the
   largest of 7,069 sites. The idiom drawn from it covers the head only, with no path capture, because the sites load
   their path at different places after the getter's call. It had 7,151 hits, the 7,069 sites among them, and every
   hit was refused: 7,081 for the path's text, 47 for the static's section, 23 unreadable. So no singleton was found
   (all 11 `missing`). The finder had taken the first read-only load in the block the jump skips as the path, whatever
   its text, then refused it for not ending with the suffix; at least 7,022 sites load their path later in that block,
   after another read-only load, LIKELY the log's format string (ER01 §4). The 70 refusals for section or reading are
   LIKELY hits that are no accessors: the idiom's wildcarded register bytes also match a load through a base register,
   and the finder never decoded the hit (WHY§180, §181). 12 hits passed the placement checks but not the path's; 26
   sites of other shapes lie outside the idiom. The scan could not have resolved the idiom anyway: it capped every
   pattern at 4,096 hits (WHY§182).
3. **The registration is `depends`**: it needs the task singleton's static from the FD4 finder. Nothing about
   `register_task` is known from R0.
4. **The task group's index 0 is an artefact.** One whole string of the group's name and one pointer to it, from
   which a "table" of one entry was grown; the confirm list passed its index on as a value. SPECULATION: the pointer
   is a field of entries wider than a pointer (WHY§184). No code loads the name with a small constant beside it.
5. **`game_data_man` has no RTTI under its expected name**, as a class or a struct, and the confirm list offered R1 a
   vtable of zero, which does not exist. By our rules (ARCH §6.3) such a static cannot be found offline; if R0c finds
   no type descriptor of the name in any namespace, R1 finds its slot in game and `probe-exe --static` cuts its
   pattern (WHY§185).
6. **The product name `differs`** from the leads' by an exact comparison: LIKELY a trademark sign after it. Nothing
   else of the fingerprint differs from what the design expects (WHY§186).
7. **222,133 undecodable bytes** (bytes stepped over, not instructions; about 0.5 % of the first `.text`) beside
   11,443,123 instructions. Not a gap of the decoder's: no disagreement with LLVM 18's disassembler over 279,458
   instructions of the pinned CRT and C++ library and 42,441 compiled for AVX2, AVX-512 and Zen 4. LIKELY data in
   `.text` (switch tables) and perhaps a protection layer's code (WHY§187).
8. **Two more executable sections**: a second section named `.text`, after the import table, and one of another name.
   R0 reads only the first `.text`. SPECULATION: a protection layer's code (WHY§189).

## What was fixed (R0c, engine `feat/engine`, merge 3d73624)

- The FD4 path is the load in the block whose string ends with the suffix, in any register and form, before or after
  the getter's call, or hoisted before the head; R0's rule runs beside it over the same hits (WHY§180).
- Every hit is decoded, and one whose operands are no RIP-relative loads or whose getter is no relative call is
  refused as `unreadable` (WHY§181). An idiom may expect, and the scan keeps, up to 65,536 hits (WHY§182).
- `fd4.status` says whether the idiom was derived, and the name layout is reported apart; without one, each singleton
  is `depends` and is named in game through its getter (WHY§183).
- Group tables are looked for at strides of 8 to 64 bytes; a lone pointer gives no index (WHY§184).
- Type descriptors are counted under any namespace, and the confirm list offers no vtable that does not exist
  (WHY§185). Product names are compared without symbols, in the derivation and at `gal/builds.toml`'s gate (WHY§186).
- A census of every executable section, and for each reference why no head was found (WHY§187, §189).
- None of it adds a key or a word to schema 1, which DataPiler 0.2.41's guard pins (WHY§188).
- The fake game carries R0c's variants (five more FD4 sites, a decoy of the idiom's wildcards, a table of wider
  entries), so the harness checks each end to end.
