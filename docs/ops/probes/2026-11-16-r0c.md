## What it settled

1. **The image reads as R0's did.** 11 sections, 235,897 functions, 455,004 base relocations, 10,202 complete-object
   locators with a vtable each; the character class's set of 6 classes and the player's of 2, both `derived`.
2. **The product name differs by one symbol only.** 11 characters in the version resource, 10 once symbols are
   removed, so `matches` (WHY§186). Which symbol it is, the report does not say.
3. **The FD4 finder's failure was the kit's bug, and the fix holds** (WHY§180). Of the idiom's 7,151 hits, R0c's
   finder accepts 7,081: the 7,069 sites the idiom was drawn from and 12 more hits. R0's rule, run beside it over the
   same hits, refuses them exactly as R0's report did (7,081 for the path's text, 47 for the static's section, 23
   unreadable). `fd4.status` is `derived`.
4. **Where the paths are loaded.** At every one of the 7,069 sites, and for every accepted hit, the path is loaded
   after the getter's call, in one of three nearby places (6,839, 226 and 4 sites), by the same instruction into the
   same register, with exactly one other read-only load between the jump and it; none is hoisted before the head.
   That is the order ER01 §4 gives, so the load before it is LIKELY the log's format string (WHY§180).
5. **The 70 odd hits are no accessors.** Each fails to decode as the idiom's instructions and is refused as
   `unreadable` (R0's 47 and 23 together), as WHY§181 expected.
6. **Part 2's scan resolves the idiom**: 7,081 hits kept and 70 rejected, the finder's own split (WHY§182).
7. **The singletons cannot be named offline** (WHY§183). The accepted hits use 217 class objects, 219 statics and one
   getter. 213 of the class objects lie past the raw data the file holds of their section (zeros until the game writes
   them), none of the 217 has a base relocation in its first 128 bytes, and no name layout reads a single one. So the
   names are written at run time: all 11 singletons are `depends`, and the confirm list asks R1 for the name layout.
8. **The task group's table is real** (WHY§184). The one pointer to the group's name lies in a table of 168 entries,
   each wider than a pointer; code addresses each entry at its start, ahead of the name field, and no instruction
   addresses the name itself. No field of the entries holds an index, so the index is the entry's place. The group is
   `derived`, and its index goes to R1 to confirm.
9. **`game_data_man` has no RTTI anywhere**: no type descriptor of the class's name in any namespace (WHY§185). Its
   slot is R1's to find, by what the instance holds (WHY§193), and the confirm list no longer offers a vtable.
10. **The undecodable bytes cost the finder nothing** (WHY§187). Of the 9,837 references to the paths, none is lost
    because decoding from its function's entry missed it. In the first `.text`, 222,133 bytes were stepped over (about
    0.5 %, as in R0) in 145,559 runs: 24,011 of the runs start right after an instruction that does not fall through
    (data after code), 6,137 start with a VEX, EVEX or XOP escape byte, and 24,802 of the bytes (about 11 %) lie inside
    functions of the exception directory.
11. **The other executable sections, decoded for the first time** (WHY§189). The small one of another name: 12,410
    instructions, 108 bytes stepped over, no reference to a path. The second `.text`: 5,160,765 instructions and
    576,857 bytes stepped over (about 3 % of it, six times the first's share) in 381,908 runs, of which only 19,959
    follow an instruction that does not fall through and 25,135 start with an escape byte; none of those bytes lies
    inside a function of the exception directory, and 590 of its instructions address an FD4 path. That fits WHY§189's
    SPECULATION (a protection layer's code) without showing it; the derivation's site search reads none of it.

## What R0c leaves for R1

R1 (WHY§193) runs in game with `probe/eldennet.dll`, part 6 of the first in-game build (`feat/engine`, merge f241700).

- **The names**: each of the 217 class objects named through its getter (ARCH §6.2 step 3), which gives the name
  layout and the 11 singletons' statics, `cs_task` among them.
- **The registration**: `register_task` has no candidate offline (`depends`); it follows from the task singleton's
  static once named, with its ABI from the game's own call sites.
- **The task's shape**: the leads name no task base (a marker of ours), so the base class, the run slot and the object
  size come from R1's hub census and its one call.
- **The confirm list's nine items**: the name layout, the two vtable sets (6 and 2 classes), the group's index in the
  loaded table, the run slot, the object size, `game_data_man`'s slot (the rising-counter search) and
  `global_hinstance`'s (the module's base), then the layout's fields; `probe-exe --static` then cuts the statics'
  patterns offline.
- **Only if a lead's singleton is not among those named**: the 26 sites of the five other head shapes (12, 8, 3, 2
  and 1), which the idiom does not match; the 2,742 references with no site (94 with a head whose jump does not pass
  them, 676 after a compare of a RIP-relative quadword with zero, 1,379 after a 64-bit load of a `.data` static, 593
  with none of these within 24 instructions); and the 590 references from the second `.text`.
