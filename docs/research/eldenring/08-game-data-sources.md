# Game data sources for the roster: online datasets, Smithbox and a reader of our own

> **Scope:** where the numbers the roster needs can come from (NpcParam rows and their `nameId`, entity ids, flag blocks, talk ids, model ids and boss-bar name ids, for the base game and Shadow of the Erdtree): online databases and datasets, DSMapStudio and the tools around it, and a Python tool of our own. It answers the owner's request of 2026-11-08 behind O54, and reads Smithbox's licence and AI stance for O55, the owner's choice of Smithbox as the source our tools read. Every id from any source is a **lead** until S1, S2 or S6 sees it in game (O48).
> **Research date:** 2026-11-08. **Game state:** patch 1.17.2 (exe 2.7.2.0, regulation 1.17.3; ER01 §1). Each source below is pinned to a commit or a date, with its DLC coverage.
> **Evidence tags:** as in [the research README](../README.md): **FACT** (seen in a primary source read here, cited with its commit or URL and date), **LIKELY**, **SPECULATION**.
> **Method:** four sweeps (online sources, tools, file formats, EldenNet's own needs) and two independent fact-checks of every critical finding, all on 2026-11-08 (the [Verification log](#verification-log) lists what they changed). Other projects were cloned shallow or blobless into an untrusted folder outside the repository and read with `git`, `grep` and `python3 -I` scripts kept elsewhere; nothing was built, installed or run, and nothing was posted anywhere. `git ls-remote` on 2026-11-08 showed every default branch still at the commit read, and Smithbox's `LICENSE`, fetched again from raw.githubusercontent.com at `e2dbcae`, matched the clone byte for byte. **Reachable:** github.com (pages and git), raw.githubusercontent.com, PyPI and Hugging Face. **Not reachable** (DNS or proxy refusal): Fextralife, Fandom, wiki.gg, soulsmodding.com and its old wikidot, soulsmods.github.io, Nexus Mods, Map Genie, Google Docs, Kaggle, web.archive.org, gitlab.com, the Elden Ring Fan API, api.erdb.wiki, www.radgametools.com and docs.python.org; Steam (steamcommunity.com and store.steampowered.com) was not retried in the sweeps, and both refused through the proxy when the note was revised the same day, so the Steam forum thread in Sources and the game's EULA were not read; gnu.org is refused, and the GitHub REST API is refused for third-party repositories. Claims about those sites rest on search snippets and are LIKELY at best. EldenNet was read at `design/v1-proposal` @`9cd61ea`. No game text, param dump, developer label or id list is copied here; the few numbers are format facts, or examples with their source. Smithbox commits FromSoftware's regulation files (§3.1): the clone holding them stayed outside the repository and none was opened (one check fetched one such blob into a blobless clone; it was deleted unopened, and later commands ran with lazy fetching off).

## TL;DR

- **Smithbox may be adopted as O55 says, under five conditions (§3.1).** Its licence is plain MIT with no AI clause. It is openly built with an AI coding agent, the opposite of me3, and nothing in its terms restricts us. But:
  1. Its repository commits 28 Elden Ring `regulation.bin` files (regulation versions 1.00.0 to 1.17.3) and game textures (vanilla LIKELY; none opened). So EldenNet never bundles, mirrors or redistributes Smithbox, and our tools read only exports made from the owner's own install, never its bundled files.
  2. Part of its bundled metadata is FromSoftware's (paramdefs, "mostly official" per Paramdex's README; Japanese developer row names and their machine translation, the developer flag-label dump), the rest is partly AI-written, and its machine-written planning notes cite fromsoftware-rs for names and offsets. So under O48 our tools take **numbers only** from the owner's own data, never Smithbox's names, annotations or layouts as facts.
  3. Its built-in me3 features (launch a project with me3, build a me3 profile) are never used (O47).
  4. Its loopback gRPC server (Soapstone, on by default) has write calls, one of which writes params into the running game's memory, and no authentication beyond the loopback bind. It runs only while `System_Enable_Soapstone_Server` is true in Smithbox's `Startup.json`, with no switch in the app, so the owner sets that to false unless a read-only client of ours is in use. A client of ours, if any, uses read calls only.
  5. It ships SoulsFormats under GPL-3.0, whose duties fall on whoever redistributes it, not on reading its exports (LIKELY; not legal advice).
- **Is there an online database we could use? Not as the source** (§2). No maintained, licensed dataset holds NpcParam rows with `nameId`, entity ids, flag blocks, talk ids, model ids and boss-bar name ids for the base game and the DLC. The wikis hold no ids, and Fandom's terms reportedly bar scraping and AI training (LIKELY). Among the sources read, vanilla `nameId`, entity and boss-bar ids appear only in an all-rights-reserved randomiser, a partly overhaul-derived map mod and decompiled overhaul scripts; the unreachable Souls Modding wiki and a Nexus Mods article may hold more (LIKELY). Licensed **leads** exist for labels and flags: Smithbox's community labels (MIT), FromSoftSaveManager (Apache-2.0) for each character's flag block, the Quest Log mod (MIT) for quest flags and talk wiring, SoulSplitter (GPL-3.0) and EROverlay (MIT) for boss defeat flags, and the eventparam dump for the base game's flag layout.
- **Which source should we use?** Decided: Smithbox (O55). The owner exports from their own install, our tools read the exports on the owner's PC, names stay there and only numbers and ids leave. Every other source is a lead for cross-checking (§6).
- **Extract with DSMapStudio, and a Python tool to work with it?** DSMapStudio stopped before the DLC (its last release, 1.11.1 of 2024-06-20, says it does not support the new Elden Ring update); Smithbox is its maintained fork, and its default branch reads regulation 1.17.3. Neither can be driven by a script: Smithbox is a Windows GUI that ignores command-line arguments. So a Python tool works **on its exports**: param CSV (NpcParam, TalkParam and others) and text JSON (NpcName, PlaceName), read with the standard library alone, about 3-5 person-days (design A, §4.2). Smithbox gives no readable export of map placements or event scripts (MSB and EMEVD files come out only raw and Oodle-compressed, and its map data export is a stub); talk scripts come out decompressed, one file per click. Reading the install directly (design B, §4.3) costs about 20-30 person-days and puts Oodle and the game's keys on us.
- **Recommendation (§6): option (b),** a small standalone research script now, on Smithbox's param and text exports, run by the owner on their PC: names into a git-ignored local census, numbers into a lead file. Entity ids, model ids, boss bars and flag blocks wait for the in-game captures (S1, S2, S6), with the public leads meanwhile. First, `.gitignore` needs `roster.local/` and `drafts.local/`, and a numbers-only check is needed before any file leaves the PC (§5).

**Across the sources:**

- **The DLC's flag labels are not published.** Both developer dumps (eventparam and Smithbox's copy of it) stop before the DLC maps (FACT); DLC flags exist only in curated sets, so every DLC block is a lead for S6.

## 3. Tools

### 3.1 Smithbox: licence, AI, and what bears on using it

All FACT at vawser/Smithbox @`e2dbcae` (2026-11-08) unless marked.

- **Activity.** 3,921 commits since 2024-01-07; 1,590 by 26 author names in the last twelve months, 1,318 of them by its maintainer. Latest release 2.2.6 (2026-09-20: "Updated the Param Upgrader for ER regulation 1.17.1"); 2.2.5 (2026-08-29) added ER 1.17.0 support. The default branch already carries regulation 1.17.3 (`11730034`, the upgrader's MaxVersion). Development builds are GitHub Actions artefacts.
- **Licence.** `LICENSE`: "MIT License / Copyright (c) 2025 Vawser / Copyright (c) 2018 Katalash, Meowmaritus", then the standard MIT body, with no added terms and no NON-AI clause (commit `6aa5266`, 2026-05-25, restored the earlier copyright holders). `src/Smithbox.Data/Licenses/` ships Smithbox's own copy (MIT, "Copyright (c) 2025 Vawser"), DSMS (MIT), ESDLang (Apache-2.0), HKLib (MIT), Tracy (BSD-3-Clause), coremats-templates (Apache-2.0), **SoulsFormats (GPL-3.0)** and a Six Labors community licence-key file; SoapstoneLib carries its own MIT licence ("Copyright (c) 2022 thefifthmatt") at `src/Andre/SoapstoneLib/LICENSE`. None has AI, LLM or training wording. Its SoulsFormats fork (`src/Andre/`) has no licence file of its own; SoapstoneLib's is the only one under `src/Andre/`. Shipping GPL-3.0 code makes the distributed program carry GPL-3.0 duties, which bind redistributors (LIKELY). We run it as a player does and read the files it writes, copying no code, so neither licence reaches EldenNet's code (LIKELY; not legal advice).
- **AI.** README "AI Disclaimer" (lines 120–121, commit `d7d403e`, 2026-05-04) states, in our words, that an AI coding agent was used to generate code and metadata within Smithbox (the original names an agent product and a model; EldenNet files paraphrase it). The repository has an agent instruction file and 47 agent planning notes. `CONTRIBUTING.md` (156 lines) and the three issue templates have no AI wording. Nothing restricts LLM use of the tool or its output.
- **Game files inside (FACT for presence; vanilla LIKELY, none opened).** 28 Elden Ring `regulation.bin` files, one per regulation version in 28 folders from 1.00.0 to 1.17.3 (not every patch has one; 1.17.3 is a regulation number, carried by patch 1.17.2), under `src/Smithbox.Data/Assets/PARAM/ER/Regulations/`, and 27 more (to 1.17.1) under `Smithbox.Release/Output/`, besides 14 for Armored Core VI and 17 for Nightreign. `ParamUpgrader.cs` loads them as "oldVanilla". It also commits world-map and compass texture binders (`*.tpf.dcx`) and, among its game-information dumps, a game script. **Consequences:** EldenNet never bundles, mirrors or redistributes Smithbox or any part of it, and never directs anyone to its bundled game files (the regulation files and textures); pointing a player to Smithbox itself for an export from their own install, as ARCH §12.3 does, stays allowed; our tools read only exports from the owner's own install and project, never Smithbox's bundled regulations; a clone of it never enters a repository.
- **Bundled metadata that is not community-written.** Paramdefs (Paramdex's README calls them "mostly official"; Paramdex took its ER definitions from Smithbox in `20512f4`); Japanese NpcParam and TalkParam row names with an "English (Machine Translated)" copy; FromSoftware's event-flag label dump under `Documentation/Game Information/ER`. TalkParam row names are dialogue and NpcParam names include character names: game text, local only. As the AI disclaimer covers "metadata", every Smithbox label is a lead to check, never a source.
- **fromsoftware-rs in its machine-written notes.** Four agent planning notes in its `Documentation/` folder use it: `MSBE Consumer Tracing Plan.md` and `MSBE Exe Analysis.md` take names and offsets from fromsoftware-rs, `TAE Template ER Analysis.md` (lines 104–105) uses the crate's layout for the slots it fills, and `Navmesh Face Data Bits.md` (line 41) cites it for a field. In `Tools/TaeTemplateSurvey/`, `er_names.txt` line 2 cites the fromsoftware-rs crate as evidence for the names it applies to the shipped ER TAE template (`Smithbox.Release/Output/Assets/TAE/TAE.Template.ER.xml`), and `ParamTrace.cs` line 267 takes slots from the crate's `ChrInsModuleContainer`. `git grep` finds no reference under `src/`, but the shipped template carries names applied from that survey. So some of Smithbox's newer field names and annotations may come in part from fromsoftware-rs (LIKELY), which makes the rule "numbers from the owner's own data only, never Smithbox's names, annotations or layouts as facts" necessary under O48.
- **me3.** README line 48 recommends me3 and says Smithbox can create a me3 profile; the project screen offers "Launch this project with ME3." and "Create a basic ME3 profile for this project." (`Assets/Localization/English/Project-GUI-Configuration.json:45, 53`; `ModEngineHandler.cs`). Our workflow never uses them (O47).
- **Soapstone.** A gRPC server, started by default, on `http://127.0.0.1:22720` (`KnownServer.cs:19`), host-checked to localhost (`SoapstoneServer.cs:273, 283`) and with no other authentication, so any local process may call it. Since PR #522 (2026-07-02) it has write calls (`ExecuteMassEdit`, `SetParamCell`, `ReloadParams`). `ReloadParams` writes param cells into the running game's process with `WriteProcessMemory` (`SoapstoneService.cs:805-860`, `ParamReloader.cs:242-382`), and `OpenResource` changes the editor's state. A client of ours would use read calls only. The server starts only while `System_Enable_Soapstone_Server` is true (`Application/Startup.cs:22`, default `true`; `Smithbox.cs:608`), a setting read from `%LOCALAPPDATA%\Smithbox\Configuration\Startup.json` (`Startup.cs:35-37`). Those are its only two references, and the developer panel only shows whether the server runs (`Developer/Tools/TaskViewer.cs`), so there is no switch in the app at `e2dbcae`: the owner sets it to `false` in that file while no read-only client of ours needs the server.
- **Network and authors.** The only hosts in its code are GitHub's (the updater, `ProgramUpdater.cs`); no telemetry host was found. Its history has no commits by me3's or fromsoftware-rs's authors (a name search of the shortlog). Its lineage is DSMapStudio (soulsmods), and it bundles SoapstoneLib (also hosted by soulsmods). O47 and O48 name only me3 and fromsoftware-rs, so none of this excludes Smithbox. The same-community argument against fstools-rs (§3.2) would, taken literally, reach Smithbox's ancestry too; the difference is that fstools-rs's code owners are those two projects' authors themselves (§7, question 5).
- **Platform.** Windows 7–11, 64-bit; the projects target `net10.0`; a Vulkan 1.3 build, or an OpenGL build without the viewport. It reads the game's encrypted archives without unpacking and copies the game's own `oo2core_6_win64.dll` from the Game folder into its program folder for Elden Ring (`ProjectEntry.cs:519-539`): that use of Oodle is Smithbox's, on the owner's PC.

## 4. A Python tool of our own

### 4.1 Which files hold which ids, and what decoding each needs

Paths are inside the game's `Game` folder; counts and archive placement are from Smithbox's `ER-File-Dictionary.json` (130,951 entries, paths only). FACT for the layouts as Smithbox's SoulsFormats fork and its 010 Editor templates describe them; each is a lead until our own reader checks it (O48).

| File | Holds | Container | Decoding needs |
|---|---|---|---|
| `regulation.bin` (loose) | NpcParam (row id, `nameId`), TalkParam (row id, `msgId`) and the other params | AES-256-CBC (IV = the first 16 bytes; a 32-byte constant key, not copied here) → DCX (ZSTD since the DLC, zlib DFLT before) → BND4 of `.param` files | AES; Zstandard; the regulation key |
| `msg/<lang>/item.msgbnd.dcx`, `item_dlc01`, `item_dlc02` (archive `data0`) | NpcName (18, 328, 428) and PlaceName (19, 329, 429) | DCX KRAK (LIKELY) → BND4 → FMG | Oodle; archive keys unless unpacked |
| `map/mapstudio/mAA_BB_CC_DD.msb.dcx` (1,349: 937 in `data2`, 412 in `dlc`) | Enemy (type 2) and DummyEnemy (10) parts: `EntityID`, `NPCParamID`, `TalkID`, `ThinkParamID`, `CharaInitID`, model | DCX KRAK (LIKELY) → MSBE, table version 73 | Oodle; archive keys unless unpacked |
| `script/talk/mAA_BB_CC_DD.talkesdbnd.dcx` (36, `data0`) | `t<talkId>.esd`: `TalkToPlayer` (bank 1, id 1; a TalkParam row), `SetEventFlag` (1, 11), function `GetEventFlag` (15) | DCX KRAK (LIKELY) → BND4 → ESD (ezstate bytecode) | Oodle, or Smithbox's File Browser export (decompressed) |
| `event/*.emevd.dcx` (589 in `data0`, 117 for `m61`) | `2003[11]` "Display Boss Health Bar" (state, entity id, slot, name id); `2003[12]` boss defeat and banner; `2003[15]` | DCX KRAK (LIKELY) → EMEVD (version `0xCD`, the Sekiro variant) | Oodle; resolving shared events |
| Archives `Data0`–`Data3`, `DLC`, `sd/sd`, `sd/sd_dlc02` (`.bhd` + `.bdt`) | every file above but `regulation.bin` | BHD5 header RSA-encrypted with a public key per archive; 64-bit path hashes; AES-128-ECB over listed ranges | the archive keys and path names (BinderKeys lists both); not needed if the owner unpacks once with Smithbox or Nuxe |

What a reader would rely on:

- **PARAM.** A row table of (id, data offset, name offset). The row size is not stored: it is the stride between rows, and a definition applies only if ParamType, DataVersion and stride all match. Elden Ring's rows carry no names. **Definitions are not in the game files:** Paramdex's (no licence, "mostly official", not version-aware) or Smithbox's (version-aware, with `FirstVersion` and `RemovedVersion`). Both give (LIKELY: computed from the definitions, not checked against a game file) NpcParam at DataVersion 9, rows of 736 bytes, `nameId` (s32, -1 for none) at byte 12; TalkParam at DataVersion 4, rows of 96 bytes, `msgId` (s32, -1 for none) at byte 4 (the signed types and the -1 defaults are FACT from both definitions, `s32 nameId = -1` and `s32 msgId = -1`; that -1 means none is LIKELY, so a reader must never read these fields as unsigned); the same at regulation 1.00.0, 1.10, 1.12.1 and 1.17.1. Smithbox's definitions mark layout changes at 1.12.1 (241 fields) and 1.17.0 (33), so a reader must refuse a layout it does not know.
- **Version.** The BND4 version string, for example `11711000` for 1.17.1.
- **FMG.** Version 2; groups of (offset index, first id, last id); 64-bit offsets to UTF-16 strings, 0 for no text. Which container wins when an id is in more than one is not established (SPECULATION: the later one).
- **MSBE.** `EntityID` is the first u32 of a part's entity block; the enemy data starts with two zero ints, then `ThinkParamID`, `NPCParamID`, `TalkID`. DSMapStudio, SoulsFormatsNEXT and Smithbox agree on these; other fields are still being renamed. `EntityID` is 0 for many generic enemies (ER01 §5.4).
- **EMEVD.** Boss bars are often set inside shared events started by `2000[0]` or `2000[6]`, whose parameter table splices the caller's values into the callee's instructions: reading a bar's name id means resolving each start call, not only scanning for `2003[11]`.
- **Talk ESD.** Every argument is ezstate bytecode; that Elden Ring uses the older games' bytecode is LIKELY (ESDLang decompiles all of them with one engine). Only the constant first arguments of the three calls above are needed.

### 4.2 Design A: read Smithbox's exports (O55)

**What the owner exports, per game version** (FACT for the menus and paths, from Smithbox's code):

1. A Smithbox build that supports the owner's regulation: the default branch knows 1.17.3, while release 2.2.6 names 1.17.1; whether 2.2.6 reads 1.17.3 correctly is not established. Our tool records the build.
2. A project whose project (mod) folder is a **new, empty folder** outside the `Game` folder and outside any git checkout (or under the ignored `/game-export/`), with the `Game` folder as its data folder, so the primary param bank falls through to vanilla (LIKELY; Smithbox exports the project's primary bank). Smithbox has no project without a project folder: one that does not exist fails the project's checks (`ProjectEntry.cs:151-160`; the field asks the user to "Pick the folder your mod is kept in."), and that folder is layered ahead of the game's own files (`ProjectVFS.cs:38-45`). The `Game` folder itself is never made the project folder, or Smithbox's saves would write into the install.
3. **Params:** Param Editor > Data Transfer > Export, mode File, "Selected Param" for NpcParam and TalkParam (later CharaInitParam, NpcThinkParam, BonfireWarpParam, WorldMapPlaceNameParam, SpEffectParam), or "All Params", which writes one `<ParamName>.csv` per param (`ParamDataExportTab.cs`, `ParamDataTransferTool.cs:337-349`). Exporting all fields lets our reader check the header.
4. **Text:** Text Editor, the owner's language, containers `item`, `item_dlc01` and `item_dlc02` (and `menu*` only if `kb-draft --check` needs TalkMsg): Export Text > Export Selected Container, written by default to `<project>/.smithbox/Workflow/Exported Text/<name>.json` (`FmgExporter.cs:29-55, 345-375`).
5. Everything stays in a git-ignored folder on the owner's PC (`/game-export/` is ignored today; §5). Text JSON goes to `<project folder>/.smithbox/Workflow/Exported Text/` unless the Text Editor's Data Transfer tab has an export directory set (`TextUtils.cs:2310-2313`; `FmgExporter.cs:128-130, 147-149`); param CSV goes to the export directory the owner picks (`ParamDataTransferTool.cs:296-341`). Pointing both into the project folder keeps every export in one place.

**How our tools read them:**

- **Param CSV** (`Tools/ParamIO.cs:18-96`): a header `ID`, `Name`, then the internal names of the fields valid for the loaded regulation version; one line per row: the id, the row name (the separator inside a name replaced by `-`, `null` if none), then each cell as text. The separator is `,` by default (a configured `|` is reset to the default). Our reader uses Python's `csv` with the recorded separator and requires `ID` and `nameId` (TalkParam: `msgId`) in the header, reads both as signed and treats a negative value as no name (§4.1), exactly as many cells per row as header fields (SPECULATION: a cheap guard, since the header is version-filtered and the cells are not), integers in the columns it uses, unique ids and at most 65,535 rows. The `Name` column is Smithbox's label (community, developer or machine-translated, and for NpcParam often a character's name): kept local, a lead for the human reviewer only.
- **Text JSON** (`StoredFmgContainer.cs:26-53`, `FMG.cs:13-33`): `{Name, SourceContainer, SourceCategory, FmgWrappers: [{Name, ID, Fmg: {Name, Entries: [{ID, Text}], Version, BigEndian, Unicode}}]}`; `SourceContainer` is missing from older exports. `fmg-import` picks wrappers by `ID`, checks the wrapper's `Name` as a second key, writes ids and texts into the local `fmg-<lang>.db`, records the container of each entry, and never prints text.
- **The census join** (SPECULATION, design): NpcParam rows whose `nameId` exists in NpcName, grouped by `nameId`; names only into `roster.local/`; ids and numbers into the lead file with `verified = false`. A leak check before every commit: no string from the local database appears in any tracked file.
- **Provenance, recorded by our tool, never typed:** the exe's product version, the SHA-256 of `regulation.bin` (no decryption), whether the DLC is installed, the language, the Smithbox build and the date.

**Smithbox's other paths** (FACT at `e2dbcae`):

- **File Browser.** It writes a container file raw, so MSB and EMEVD come out still KRAK-compressed (`FileExporterTool.cs:99-135`; `FileUnpackerTool.cs:297-335` unpacks all archives the same way). It also writes one internal file of a binder at a time with the binder's DCX removed (`ExportInternalFile`, `FileExporterTool.cs:146-307`; `BND4Reader.cs:63-71`): a `t<id>.esd` from a talk binder or an `.fmg` from a msg binder comes out decompressed, so our side needs no Oodle for them, at one click per file.
- **Global MSB search** (`MsbSearchTool`, added in `4d37a59`, 2026-11-06): searches every map of the project and copies result lines to the clipboard, each `name <alias> [category: type] field = value`, one field per line and no map id (`MsbQueryRunner.cs:253-300`). Weak as a source, since entry names repeat across maps.
- **No map data export** (a stub, `MapDataTransferTool.cs:79-99`), and no EMEVD or talk ESD editor (README lines 38–40 send users to DarkScript3 and ESDLang).
- **Soapstone, read calls.** `ListParams`, `ListParamRows` and `GetParamRows(paramName, rowId, vanilla)`, where `vanilla = true` reads the vanilla bank (`SoapstoneService.cs:1009-1060`). Map entries come through `SearchObjects`, `GetObject` and `BatchGetObjects` with properties by name, but only for maps loaded in the active map view; `OpenResource` queues a map load. A read-only client could pull placements map by map (SPECULATION as a workflow; time and memory for 1,349 maps unknown).

**Recommendation: (b).** It answers the owner's request (the game's ids, usable whatever the blueprint brings) for about a week of work at most, needs no keys, no Oodle and no binary parsing, and keeps Smithbox at arm's length: its files in, numbers out. What (c) and (d) add are the numbers the design already captures in game (S1's entity ids, S2's bars and holders, S6's flags), which must verify them anyway. ## 7. Open questions

2. **Keys.** Should a tool of ours decrypt `regulation.bin` or the archives? (a) No, Smithbox does; (b) yes, with keys read at run time from a local file the owner supplies, never committed; (c) commit the keys. **Recommendation:** (a). (b) adds little, since a second reading shares the same paramdefs (§4.3); never (c).
3. **How much of an id index may be committed, and where?** (a) Only the ids a feature binds (rows per form, `nameId`s, entity ids, bar ids, flag block bases); (b) a fuller numbers-only extraction, such as every NpcParam row with a `nameId` set (not negative, §4.1). **Recommendation:** (a): a whole param column comes close to the "params" CLAUDE.md forbids. DESIGN §7.8 gives the index its home in `identity/characters.toml`; a research copy under `docs/research/` before the blueprint would be a new home (SPECULATION), so the owner's call.

5. **Projects close to the excluded ones.** O47 and O48 name only me3 and fromsoftware-rs. fstools-rs has no clause in its files, but its code owners are those two projects' authors; SoulsRandomizers is all rights reserved, with an anti-LLM rule for contributions. **Recommendation:** use neither, not even as leads, and post or contribute in neither. 6. **Slugs.** The committed index may carry our slugs, and persona ids are already name-like. **Recommendation:** base each slug on the name a first meeting shows, never on a later form or a reveal; GraceUI's URLs stay on opaque ids.
